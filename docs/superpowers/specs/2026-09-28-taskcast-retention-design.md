# Taskcast 通知合并与历史保留策略

日期：2026-09-28

状态：用户已于 2026-09-28 整体确认；进入实施计划阶段，尚未实现或启用线上清理。

范围：WonderAgent 的搜索刷新通知，以及 Taskcast 的终态任务保留机制。

## 目标与已经确认的边界

用户希望减少 Taskcast 中没有必要长期保存的刷新通知，同时让不同任务类型使用不同保留规则。

已经确认：

- 按任务类型配置默认策略，创建单个任务时允许覆盖。
- 未配置策略的任务保持现有行为。
- 首版只自动清理终态任务，保留期限从任务结束时开始计算。
- 运行、暂停、等待输入等非终态任务不自动删除历史。

本稿将事件历史与任务记录的期限分开表达。下文的 WonderAgent 天数、首版支持范围、存量接入和接口行为已经通过整体审阅，但并非已经执行的线上配置。

审查应结合项目核心需求、实际使用场景和现有运行约束，避免过度设计。保留现有恢复和兼容要求，不扩展到通用数据治理、外部归档平台或管理后台。

## 现状依据

- WonderAgent `TaskcastPublisher.publishExecutionEvent` 发送严格的 `type/runId/entityId?/revision` 通知，未设置 series；客户端通过业务快照读取结果。
- Taskcast v1.6.1 已支持 `latest`、Redis 安全归档释放、持久化 TTL 和后台生命周期任务。
- 既有 `cleanup.rules` 包含类型、状态、时间和事件筛选声明，但没有接入自动删除的执行流程。
- PostgreSQL 任务记录与事件、series 状态、归档收据、分配及终态 outbox 存在关联。Redis 也保存事件、序号与写入控制状态，不能只删一张表或一组 key。
- 本次会话的生产只读样本为 115 个任务、595,192 条事件，事件表及索引约 705 MiB，Redis 约 236 MiB。这个样本说明优化动机，不作为后续操作的删除清单。

## 方案选择

1. **推荐：复用 Taskcast 的 series 与 cleanup 接口。** WonderAgent 表达通知语义，Taskcast 负责存储一致性和到期处理。沿用现有任务级覆盖形式，减少新概念。
2. 仅由应用定时执行 SQL 删除：需要每个应用理解 Taskcast 的 Redis、归档及 outbox，容易破坏恢复关系，不采用。
3. 新建独立保留策略服务：增加部署和接口维护成本，当前需求不需要，不采用。

## WonderAgent 通知合并

- 对普通刷新通知设置稳定的 `seriesId` 与 `seriesMode: latest`。分组边界为 Taskcast task ID + 事件类型 + entityId（无 entityId 时使用任务级组）。
- 首版允许合并的事件为 `search.run_changed`、`search.profile_session_changed`、`search.candidate_changed` 和 `search.candidate_surfaced`。
- `search.failure_created`、`search.run_drained`、`search.local_creator_refresh_requested` 保留逐条语义，避免把失败发生、完成信号或请求类事件作为普通状态覆盖。未来新增事件默认不合并，明确语义后再加入。
- 保持原事件类型和 data 不变，现有订阅者仍可解析；不同实体和不同事件类型不互相覆盖。
- 每次发布仍推送给在线订阅者。合并减少历史保留和重连回放，不等于减少实时发布请求次数。
- `latest` 指 Taskcast 接收顺序的最新通知，不是业务 revision 的排序器。业务快照和客户端 revision 校验继续作为正确性依据；不为本次优化新增分布式 revision 排序服务。
- 旧的无 series 事件不会被新 series 自动吸收，本项主要控制新增数据；存量处理属于后续保留策略接入。
- 此次不一并增加 SSE 游标协议改造；合并后的通知、初始快照和既有断线重试均需验证。

## 策略模型

继续使用 `cleanup.rules`，不引入第二套与它重叠的 `retention` 配置。

### 解析与覆盖

1. 创建任务时提供 `cleanup`，则完整采用任务自己的规则数组，替代类型默认规则，不做逐字段合并。
2. 显式 `cleanup: { rules: [] }` 表示该任务不自动清理。
3. 未提供任务级配置时，取全局规则中匹配任务类型的规则，保存为该任务的有效策略快照；状态条件保留到结束时判断。
4. 没有匹配规则则不自动清理。修改全局默认值只影响之后创建的任务，不追溯修改已有任务。
5. 为有效策略保存最小的版本/解析标记，区分新机制已接管的任务与历史上仅保存了 cleanup JSON 的任务；不复制事件正文或配置全集。

Taskcast 只理解调用者提交的任务类型和状态，不查询 WonderAgent 的业务数据库。

### 时间与删除目标

- `trigger.afterMs` 从持久化的 `completedAt` 计算，不因普通读取、重试或清理自身更新而重新计时。
- 旧记录缺少可靠结束时间时先跳过；不猜测结束时间或直接按创建时间删除。
- `match.status` 可以区分 completed、failed、cancelled、timeout；任何非终态都不执行。
- `target: events` 删除任务事件历史，保留任务 ID、身份、最终状态、result/error 等任务记录。
- `target: all` 删除任务及其关联数据，表示任务记录的保留期结束；事件历史至迟同时结束。
- 同一有效策略中的规则分别生效。匹配多条事件规则时，以最早到期的删除规则生效；`all` 是整个任务的最终保留上限，不建立隐式的通配符优先级。

### 首版范围

首版实现按任务类型/终态选择、整份事件历史到期删除和整个任务到期删除。暂不增加运行中滚动窗口、按条数/字节上限淘汰、按事件类别删除部分历史。

现有 `eventFilter` 和 `target: task` 仍可在未启用清理的兼容路径中读取与保存。启用自动清理的有效策略如果包含这些首版未支持的能力，应在配置/创建边界明确拒绝，不能默默忽略后扩大删除范围。文档须修正当前“task 可以只删除任务而留下事件”的承诺，因为当前数据库外键会级联删除事件。

这个范围满足按任务种类区分保留需求，同时避免在首版引入任意事件孔洞、混合 series 快照与归档证明重写的问题。

## 配置例子与 WonderAgent 建议

新增全局清理开关，默认关闭。下面展示建议的开启后策略；实现前完善 TypeScript、Rust 配置校验和 SDK 类型。

```yaml
cleanup:
  enabled: true
  rules:
    - name: search-success-events
      match:
        taskTypes: ["influagent.search.youtube"]
        status: [completed, cancelled]
      trigger:
        afterMs: 86400000
      target: events
    - name: search-failure-events
      match:
        taskTypes: ["influagent.search.youtube"]
        status: [failed]
      trigger:
        afterMs: 604800000
      target: events
```

| 场景 | 事件建议 | 任务记录建议 |
| --- | --- | --- |
| WonderAgent 搜索 completed/cancelled | 结束后 24 小时 | 保留，不自动删除 |
| WonderAgent 搜索 failed | 结束后 7 天 | 保留，不自动删除 |
| WonderAgent 搜索 timeout | 暂不自动删除 | 保留 |
| 计划生成、Agent、LLM 等其他类型 | 未配置则保持现有行为，由对应应用明确选择 | 同左 |

`influagent.search.youtube` 是当前搜索 publisher 使用的实际类型名，本次不顺带更名。Taskcast timeout 不一定等于 WonderAgent 业务结束，因此本次应用默认策略不包含 timeout。

需要完整回放的任务可以使用更长事件期限；需要长期保留的单个任务可以用空规则覆盖默认值。不同类型的天数由应用方配置，不写死在 Taskcast 引擎中。

## 清理执行与恢复一致性

复用后台生命周期调度、任务级锁和存储写入保护，不另建队列系统。首版交付 Redis + PostgreSQL 组合的完整清理能力，并保持 Node.js/Rust 行为一致；其他存储组合保持现有行为，启用清理但适配器能力不完整时明确报配置错误。

每批从持久化存储分页领取到期任务，避免只扫描 Redis 而遗漏已释放的 cold 任务。批次和数据库操作有上限；使用稳定分页，避免一个不符合条件或持续失败的任务阻塞后面的任务。

对单个任务：

1. 在现有任务锁/并发控制下重新核对有效策略、终态、结束时间和期限。
2. 有未完成的终态投影、worker assignment 结算或归档操作时先跳过，沿用既有恢复机制完成后再尝试。
3. 先用现有受保护的归档/释放流程消除 Redis 事件副本，确认持久化覆盖和 cold 状态。对已在 cold 的任务不重复归档。
4. 在 PostgreSQL 事务中删除匹配目标及依赖数据，提交最小清理标记。整份事件过期时，同时处理持有事件正文的 series 状态及不再适用的归档收据；保留任务身份和最终状态。
5. 事件索引的最高已使用值继续保留，不重置或复用。持久化写入路径必须识别已清理的索引范围，拒绝清理前延迟到达的异步写入，防止事件重新出现。
6. 发生中断时依靠持久化标记和现有存储状态继续。Redis 已释放、PostgreSQL 尚未删除属于可重试中间状态；不得报告为清理完成。

整任务删除需确认不存在待完成的关联工作，并防止旧异步写入把任务或事件重新创建。使用现有写入者版本就绪检查隔离旧写入者；不兼容写入者仍存活时不启用删除。

清理日志只输出任务 ID、策略名称、删除数量、耗时和受控错误分类；不把逐次扫描或调试日志写入业务表。只持久化恢复及防止迟到写入所需的最小状态。

## 清理后的 API 语义

- 仅事件过期：GET task 仍返回原任务和最终结果，增加可选的历史过期时间标记。旧客户端忽略新增字段即可。
- 历史查询返回空事件集合，并通过响应头/任务标记明确历史已过期，不伪装成任务从未产生事件。
- 对终态任务的 SSE 返回历史过期提示事件，再按原协议发送 `taskcast.done`；不会因没有历史而无限等待。旧客户端可忽略新增提示，仍识别 done。
- 原事件游标不再保证可以回放。HTTP 与 SSE 都明确历史过期，调用者可查询任务结果或业务快照；不自动重跑任务。
- 完整 archive 导出返回明确的 `TASKCAST_HISTORY_EXPIRED` 冲突错误，不能导出一个声称完整但实际缺失的归档。导入逻辑不自动重新填充已清理历史；显式覆盖导入仍按现有授权和恢复约束执行。
- 整个任务过期：查询返回现有 404。WonderAgent 当前会从业务库重建缺失搜索任务，因此其默认策略保留任务记录，避免删除后又按需重建。

这些变化仅影响明确启用了清理并且已到期的任务。需要完整历史的调用者应选择足够长的期限或关闭该任务清理。

## 上线与存量

1. WonderAgent 的通知合并可以单独交付，定向验证后进入正常 CI；不依赖 PostgreSQL 清理上线。
2. Taskcast 先部署配置、数据迁移和读取兼容能力，清理默认关闭。Node.js、Rust 及全部写入者就绪后再启用目标策略。
3. 新创建任务才自动获得新策略快照。旧任务不因升级、开关开启或全局配置变化而突然进入删除队列。
4. 存量接入另做预览，列出任务类型、业务状态、结束时间、拟采用策略、事件数量和预计影响；WonderAgent 同时检查业务库的未完成/恢复工作。
5. 存量接入采用明确 allowlist、操作前复核和可恢复备份。本次设计与实现不授权直接删除当前生产数据。
6. 关闭清理开关只停止后续删除，不恢复已经删除的历史。此前已启用的 Redis 自动释放仍是独立机制，不等于永久清理。

## 验证范围

通知合并覆盖：同组替换、不同实体/类型隔离、不合并事件白名单外类型、旧事件内容兼容、并发发布、重连后快照刷新以及依赖失败恢复。

Taskcast 覆盖：

- 类型默认、任务覆盖、空数组禁用、多个规则生效、无匹配不删除、变更默认不追溯。
- 终态前不删、到期边界、结束时间缺失、成功/失败/timeout 差异、Redis 已 cold 的任务仍能被扫描。
- events 保留结果、all 清理关联、错误配置拒绝、未支持存储能力明确报错。
- 并发清理、异步迟到写入、锁丢失、归档中断、outbox 未完成、Redis/PG 不可用时可重试且不误报成功。
- 历史与 SSE 过期语义、旧客户端继续读取最终结果、归档导出不伪造完整性。
- PostgreSQL/Redis 集成测试与真实 HTTP 入口 Good Case/Bad Case，Node.js/Rust 相同契约；沿用各仓库 CI 和覆盖率门禁。

开发阶段按影响范围运行定向测试，复用同代码状态的通过结果。此稿只有文档变更，不运行全量业务测试。

## 自审结论

- 已把用户确认的边界与建议的保留天数、交付范围区分。
- 复用现有 cleanup/series 接口，不建设独立策略平台。
- 首版不支持部分事件筛选，明确拒绝，避免悄悄扩大删除范围。
- 保留存储写入保护和恢复约束；不能把 Redis flush 或 PostgreSQL 单表 DELETE 作为实现。
- 尚无线上配置修改、数据删除或产品代码变更。本稿已通过整体审阅，实施计划分别覆盖通知合并和 Taskcast 保留机制。
